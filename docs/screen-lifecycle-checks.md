# 大屏持续运行回归

本轮复现了两处恢复延迟：Socket.IO 重连只重新加入班级房间，未拉取断线期间漏掉的发布；页面从后台恢复也未主动刷新列表。两者都可能一直显示旧内容，直到下一次发布事件或五分钟兜底轮询。

`boardActions.startRealtime()` 现在在连接成功后重新订阅并拉取列表；联网恢复、回到前台和从页面缓存恢复时也会触发刷新。恢复事件和发布事件共用原有 250ms 合并窗口，避免短时间连续事件造成重复请求。新增事件监听随 `stopRealtime()` 一起移除，停止时也取消尚未执行的刷新。

测试分两层：

- `tests/screenLifecycle.test.js`：通过真实 Store 和本机 HTTP fixture 验证漏发补同步、前台恢复、事件合并、后台/离线抑制和停止清理。重复初始化 30 次后，将三个周期定时器推进一个模拟日，检查仍只有 288 次兜底刷新、1440 次心跳、2880 次队列重试，没有重复注册。
- `tests/e2e/publication.spec.js`：在生产构建的 Chromium 页面上连续进行 8 轮断网与 Socket.IO 重连，其中 4 轮使用 CDP 冻结/恢复页面。断开时发布作业，恢复后必须显示；每轮检查只有一个连接、一个班级订阅和一次重新加入，恢复刷新次数不随轮数增长。再发出 20 个连续失效通知，验证只请求一次最新版。关闭页面后检查连接和订阅归零。

运行 `pnpm test` 和 `pnpm test:e2e`；浏览器用例随现有 CI 执行。Windows 若保留默认端口，可按 `browser-release-checks.md` 设置 `E2E_WEB_PORT`、`E2E_API_PORT`。

这是加速的生命周期回归：模拟日不等于真实运行 24 小时，浏览器冻结不等于 Windows 整机休眠。这些测试也不证明长时间运行没有内存增长；真实设备长期驻留和整机休眠仍需单独观察。
