# 大屏持续运行回归

本轮复现了两处恢复延迟：Socket.IO 重连只重新加入班级房间，未拉取断线期间漏掉的发布；页面从后台恢复也未主动刷新列表。两者都可能一直显示旧内容，直到下一次发布事件或五分钟兜底轮询。

`boardActions.startRealtime()` 现在在连接成功后重新订阅并拉取列表；联网恢复、回到前台和从页面缓存恢复时也会触发刷新。恢复事件和发布事件共用原有 250ms 合并窗口，避免短时间连续事件造成重复请求。新增事件监听随 `stopRealtime()` 一起移除，停止时也取消尚未执行的刷新。

测试分两层：

- `tests/screenLifecycle.test.js`：通过真实 Store 和本机 HTTP fixture 验证漏发补同步、前台恢复、事件合并、后台/离线抑制和停止清理。重复初始化 30 次后，将两个周期定时器推进一个模拟日，检查仍只有 288 次兜底刷新、1440 次心跳，没有重复注册；空队列不再进行周期补传。
- `tests/e2e/publication.spec.js`：在生产构建的 Chromium 页面上连续进行 8 轮断网与 Socket.IO 重连，其中 4 轮使用 CDP 冻结/恢复页面。断开时发布作业，恢复后必须显示；每轮检查只有一个连接、一个班级订阅和一次重新加入，恢复刷新次数不随轮数增长。再发出 20 个连续失效通知，验证只请求一次最新版。关闭页面后检查连接和订阅归零。

运行 `pnpm test` 和 `pnpm test:e2e`；浏览器用例随现有 CI 执行。Windows 若保留默认端口，可按 `browser-release-checks.md` 设置 `E2E_WEB_PORT`、`E2E_API_PORT`。

这是加速的生命周期回归：模拟日不等于真实运行 24 小时，浏览器冻结不等于 Windows 整机休眠。这些测试也不证明长时间运行没有内存增长；真实设备长期驻留和整机休眠仍需单独观察。

## 离线作业补传退避（2026-09-05）

补传由 `screenUploadRetry.js` 调度一次性定时器。初始化、入队和联网恢复时在 0～2 秒内随机开始；连续失败后的等待范围依次为 15～30 秒、30～60 秒、60～120 秒、120～240 秒，之后保持在 150～300 秒。成功上传重置失败计数；断网取消定时器，真正恢复联网时重新从 0～2 秒开始。重复 Socket.IO 连接通知或 online 事件不会跳过已有退避。手动重试仍可立即执行，但不会与当前批次并行。

无响应、408、429 和 5xx 保留为待补传；其他 HTTP 错误保留为待人工处理，不自动重试。上传成功但本地队列写入失败时，保留原请求 ID 并使用退避重试。持久化结构、容量和过期处理规则没有改变，退避计数仅保存在当前会话内存中。

调度器按 Store 管理，停止同步后清理定时器和监听。绑定切换或重新初始化后，旧批次响应不能修改新会话或继续用新令牌上传旧队列；旧队列保留原请求 ID，后续可由服务器幂等处理。

- `tests/screenUploadRetry.test.js` 验证随机范围、指数增长及上限、恢复重置、取消与错误分类。
- `tests/screenUploadRetryFlows.test.js` 使用实际 Store、Axios 和本机 HTTP 服务验证限流/故障退避、恢复上传、请求 ID 不变、权限错误停止、绑定切换和存储失败。只控制调度时间，不模拟上传方法。

## 心跳与自动刷新并发保护（2026-09-06）

修复前的本机 HTTP 测试复现：一个未完成的心跳遇到 15 次前台事件后，共发出 16 个请求；旧心跳在绑定、令牌切换、同绑定重新初始化或停止同步后，仍将时间写回并尝试执行指令。慢列表请求期间再次收到发布事件，也会在前一个请求未完成时发起第二个请求。

`screenSyncActions.js` 现在按同步生命周期串行执行心跳，包括本次响应中的指令及回执；失败后释放占用，允许下次心跳。应用响应、执行指令、发送回执和执行延迟页面重载前，均核对绑定 ID、令牌与同步上下文。停止同步清理延迟重载定时器。已经发出的请求不会被强行撤销，其过期结果会被忽略。

远程 REFRESH_DATA 触发的配置和列表请求也接受同样的有效性检查，防止它们晚到时写入新绑定或缓存。配置加载另有请求归属检查，较早请求不能覆盖较新的请求结果；旧请求只能收尾自己仍拥有的加载状态。

`boardActions.js` 保留空闲时的 250ms 防抖，自动刷新批次开始后等待列表、教师发布列表和待处理事项请求全部结束。期间收到的发布、重连或前台恢复事件合并成一次待刷新标记，结束后补一轮；若补刷期间又有变化，再按相同规则处理。五分钟兜底刷新也进入此调度，但保持原先不主动刷新教师发布列表的行为。停止或重新初始化会丢弃旧批次的待刷新标记及过期列表响应。

该合并范围是实时事件、生命周期事件和兜底自动刷新；用户保存、切换日期等显式操作仍走原有刷新入口，没有增加等待前一个自动批次的要求。

验证覆盖实际 Store、Axios 和本机 HTTP 的慢心跳、连续前台恢复、会话变更、配置/列表晚到、正常远程刷新、页面重载、回执晚到、失败恢复，以及慢自动刷新期间的事件合并与停止清理。教师批次测试还替换两个教师动作，验证某请求失败时仍等待其他请求结束。时间被加速的测试不代表真实设备长时间运行测量。

最终本机检查：`node --test tests/*.test.js` 203 项通过；ESLint、生产构建和 PWA 校验通过。Chromium 用例继续覆盖教师发布、大屏实时更新、断网补传、PWA 升级、版本冲突和反复冻结恢复。本次仅修改前端及其测试、文档，没有修改后端、数据库或部署代理。
