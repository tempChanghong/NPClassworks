## R1 · P2：保存目标偏好失败会阻断已成功发布的收尾

位置：`src/components/v2/PublicationComposer.vue:840-841`，`src/utils/teacherTargetPreferences.js:96`。

正式发布请求已成功，随后 `rememberTeacherTargetCombination()` 写本地存储。如果配额不足等导致写入异常，会跳过 `completeSave()`，进入发布失败处理。编辑器保留正文，但未记录服务端返回的发布 ID，也没有发出成功事件。再次点击发布仍调用新增接口。

用实际组件、Store、Axios 和本机 HTTP 夹具复现：成功 POST 后 `editingBase=null`、成功事件为 0、错误为 `QuotaExceededError`；再次提交发出第 2 次 POST。夹具未模拟后端重复作业检测，因此结论是“重复发起创建请求”，不是断言线上必然新增两份作业。

建议：发布成功收尾与非关键的目标偏好保存隔离；即使偏好写入失败，也必须保留已成功发布的 ID/版本，并准确反馈发布结果。

## R2 · P3：会话初始化期间，收藏同步可能永久保持忙碌

位置：`src/stores/classworksV2/teacherActions.js:32,108-110,151`；入口包括 `src/pages/settings.vue:884`。

收藏请求尚未返回时进入设置页，页面再次调用 `bootstrapTeacher()`，增加会话版本。新初始化的同步因旧的 `teacherTargetPreferencesSyncing=true` 直接返回；旧请求回来后发现会话版本已变化，`finally` 也不清理忙碌状态。

实际 Store/HTTP 复现：所有请求完成后 `syncing=true`；再次手动同步新增网络请求数为 0。需重新加载页面或退出账号才能恢复。

建议：由具体会话/任务拥有同步状态；新初始化应能接管或重置旧任务，旧任务收尾不能修改新任务状态。

## R3 · P3：另一设备的收藏删除仍会被无关的本机更新恢复

位置：`src/stores/classworksV2/teacherActions.js:127-128`，`src/utils/teacherTargetPreferences.js:100-107,119-129`。

A、B 设备之前都已同步同一收藏；A 取消并同步后，B 不重新载入，而是发布到另一个目标，更新自己的“最近目标”。这会把整份偏好标记为 dirty，并将 B 缓存的旧收藏与远端取并集。本机没有该收藏的删除记录，因而将它重新写回远端。

复现结果：远端收藏从 0 条恢复为 1 条。删除发生在 GET 之前，无需两次 PUT 恰好并发。

建议：区分收藏新增、删除和最近目标变更；用同步基线或操作记录合并，而不是将所有本地缓存收藏视为待新增项。第三批修复的“本机离线取消后刷新”场景仍通过，此项是其他设备删除的边界。

## R4 · P2：队列重试测试误拦截 HTTP 超时定时器

位置：`tests/screenQueueReadFlows.test.js:63-76`。

测试拦截所有 15～300 秒的全局 `setTimeout`，将其计入重试列表。本轮全套 419 项中 418 项通过，此用例在第 76 行得到 `2 !== 1`。另行加栈追踪后确认，15 秒回调来自 `follow-redirects/index.js:220` 的 `ClientRequest.startTimer`，不是补传重试。单文件探测时用例又通过，但同样捕获了 HTTP 定时器，因此还存在误通过风险。

建议：对重试调度器注入可控时钟，或精确拦截业务调度入口，不按超时时长猜测回调身份。不能仅增大等待时间或放宽计数断言。
