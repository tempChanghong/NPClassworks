## F-01：教师管理列表只读取第一页，搜索和待处理分类遗漏内容

**影响对象：**使用“发布管理”和“待处理”中心的教师。数据量随使用时间增长后即可触发，不要求异常网络或并发操作。

### 触发步骤与实际结果

场景一：教师可见发布有 101 条，目标作业按服务器顺序排在第 101 条。在发布管理中搜索该作业的唯一标题。

- 预期：能搜索并打开这条作业，继续编辑、复制或查看。
- 实际：前端只收到并保留前 100 条，页面统计也按这 100 条计算；搜索只检查已加载数组，返回空结果。刷新仍只取得同一页。

场景二：待处理中有 50 条“确认后被修改”和 1 条“大屏新录入”。按照后端排序，前一种事项排在后一种之前。教师点击“大屏新录入”分类。

- 预期：分类计数为 1，列表展示对应事项。
- 实际：计数显示 1，列表却为空，并显示“这个分类已经处理完了”。

### 原因与源码依据

1. [教师发布列表刷新](../src/stores/classworksV2/teacherActions.js#L234)固定请求 `limit: 100`，随后仅保留 `result.items`；首次初始化也使用同样的限额。
2. [发布管理统计和筛选](../src/components/v2/TeacherPublicationManager.vue#L332)均基于 `store.teacherPublications`，没有获取后续页面的操作。
3. [待处理刷新](../src/stores/classworksV2/teacherActions.js#L250)固定请求 `limit: 50`。[待处理分类](../src/components/v2/TeacherActionCenter.vue#L227)使用服务器的全量 `summary` 显示计数，但筛选只处理第一页 `items`；[空列表提示](../src/components/v2/TeacherActionCenter.vue#L201)直接将其解释为该分类已处理完。
4. 后端已经提供分页能力：[发布列表](../../NPClassworksKV/services/publicationService.js#L362)返回 `total/limit/skip`；[待处理查询](../../NPClassworksKV/services/publicationActionQuery.js#L48)对列表分页、对分类计数使用全量集合，并支持按 `reason` 查询。

### 轻量复现

调用当前 `teacherActions` 中的两个刷新方法、实际发布筛选函数及待处理分类筛选表达式，API 替身按照后端的分页规则返回数据：

```text
publications 请求：limit=100，仅一次
服务器记录数=101，页面“全部”计数=100，搜索第101条的结果数=0

action-required 请求：limit=50，仅一次
“大屏新录入”分类计数=1，该分类可见事项数=0
```

数据仍在后端。先处理第一页事项可以让后续待处理向前移动，但用户无法直接处理当前被隐藏的分类。这里检查的是**教师管理接口**，与用户已修复的作业板 `/feed` 分页问题属于不同调用路径。

### 建议与修复验收

- 发布管理使用服务器分页与筛选，或完整加载后再做本地筛选；分页状态必须包含总数，不能把当前页长度当作全部数量。
- 待处理切换分类时，使用后端 `reason` 条件并分页加载，保证计数与列表处于同一查询范围。
- 不建议仅提高固定上限。验收至少覆盖 101 条发布的末项搜索，以及上述“50 条修改 + 1 条大屏新录入”的分类场景。

## F-02：删除已有异常考勤的学生后，重开工具会出现人数错误并阻止保存

**影响对象：**在大屏维护名单并记录缺勤、迟到或不计入考勤状态的教师、学生值日人员。

### 触发步骤与实际结果

1. 在“课堂工具 → 考勤”中准备张三、李四两名学生。
2. 将张三标记为缺勤，点击“保存今日考勤”。
3. 打开“编辑学生名单”，删除张三，点击“保存名单”。
4. 不再次保存考勤，关闭课堂工具，然后重新打开考勤。
5. 点击“保存今日考勤”。

预期是名单与今日考勤保持一致，剩余学生可以继续正常记录考勤。实际调用链会重新加载包含张三旧 ID 的考勤数组：页面只有到校的李四，却按数组长度显示缺勤 1、到校 0；保存被后端以 `422 / ATTENDANCE_STUDENT_INVALID` 拒绝。

### 原因与源码依据

1. [后端保存名单](../../NPClassworksKV/services/classroomToolsService.js#L97)将移除学生设为 `isActive: false`，没有同步处理已保存的考勤。
2. [前端保存名单](../src/components/v2/ClassroomToolsDialog.vue#L374)确实过滤了无效学生 ID，但只修改当前内存里的 `attendanceDraft`，没有将该变化持久化。
3. [重新打开工具](../src/components/v2/ClassroomToolsDialog.vue#L309)再次加载服务端数据；[attendanceFromStore](../src/components/v2/ClassroomToolsDialog.vue#L319)原样复制数组。[后端读取考勤](../../NPClassworksKV/services/classroomToolsService.js#L133)也原样返回旧 ID。
4. [人数统计](../src/components/v2/ClassroomToolsDialog.vue#L300)直接使用数组长度。被删除学生没有可见行，用户无法通过其状态按钮清除这个 ID。
5. [后端保存考勤](../../NPClassworksKV/services/classroomToolsService.js#L140)使用当前活跃名单校验，旧 ID 被[有效学生校验](../../NPClassworksKV/services/classroomToolsService.js#L58)拒绝。

### 轻量复现

执行实际后端名单和考勤服务函数，以内存替身模拟数据库，并执行实际前端 `attendanceFromStore()`：

```text
保存缺勤：absent=[s1]
删除 s1 后活跃名单：[s2]
重新读取后草稿：absent=[s1]
可见学生中的缺勤人数：0
顶部计算的缺勤人数：1
保存结果：422 / ATTENDANCE_STUDENT_INVALID
错误信息：考勤包含不属于当前行政班的学生
```

此问题要求删除前已有异常考勤。若保存名单后立即再保存考勤，当前内存中的过滤能够避免错误；重新打开名单、原样保存，再保存考勤也可以迂回恢复。因此它会阻断正常操作，但不是永久无法恢复的数据损坏。

### 建议与修复验收

- 明确当前可编辑考勤与历史考勤快照的规则。今日考勤读取、统计和提交应对齐当前名单，避免不可见 ID 卡住整个表单。
- 将名单变动后的当前考勤处理纳入服务端一致性逻辑，或至少在恢复草稿时过滤当前已失活学生；不要仅依赖保存名单后的局部内存清理。
- 不应为修复今日考勤而直接删除所有历史记录中的学生信息。
- 验收覆盖缺勤、迟到、不计入三类状态，并包含“保存名单后直接关闭，再重开保存”的路径。

## F-03：清空发布时间后，保存草稿和正式发布均静默失效

**影响对象：**教师发布表单。最小复现使用新建作业，不依赖已有发布或网络请求。

### 触发步骤与实际结果

1. 新建作业，填写科目、发布目标和正文。
2. 清空“发布时间”。
3. 点击“保存草稿”或“正式发布”。

预期是明确提示补填有效时间，或按约定使用默认时间。实际没有发起写入，错误提示保持为空，按钮结束加载后回到原状。用户无法判断是未点击成功、网络失败还是表单内容有误。

### 原因与源码依据

- [发布时间输入框](../src/components/v2/PublicationComposer.vue#L174)允许产生空值，没有必填校验。
- [提交校验](../src/components/v2/PublicationComposer.vue#L718)检查了科目、目标和标题正文，但没有验证发布时间；[转换 ISO 时间](../src/components/v2/PublicationComposer.vue#L747)时，`new Date("").toISOString()` 直接抛出 `RangeError`，尚未进入 store 写入调用。
- [异常处理](../src/components/v2/PublicationComposer.vue#L783)只把 `store.teacherError` 赋给 `localError`。这次错误产生于组件本地，store 错误仍为空，因此[错误提示框](../src/components/v2/PublicationComposer.vue#L407)不会显示。

### 轻量复现

提取当前组件的实际 `submit()`，使用有效科目、目标和正文，分别执行保存草稿与发布。`writes` 表示进入 store 写入函数的次数：

```text
发布时间为空，DRAFT：     writes=0，localError=""，teacherError=""
发布时间为空，PUBLISHED： writes=0，localError=""，teacherError=""
有效发布时间，DRAFT：     writes=1
有效发布时间，PUBLISHED： writes=1
```

这不是后端校验拒绝，异常发生在请求之前。复现前置条件是 store 没有残留旧错误；有残留错误时也可能显示无关提示，而非当前字段的真实问题。

### 建议与修复验收

- 在构造请求前校验时间是否为空以及是否为有效日期，并在字段旁或表单顶部显示原因。
- 组件本地异常应有独立错误处理和兜底提示，不能假设每个异常都会先被 store 记录。
- 验收同时覆盖保存草稿、正式发布，以及修正时间后的再次提交；失败时保留其他已填写内容。

## F-04：30 秒噪声历史片段混用 60 秒实时分析，区间评分和日均分失真

**影响对象：**使用噪声监测历史记录回顾课堂安静程度的人员。

### 触发步骤与实际结果

1. 在大屏课堂工具中开始噪声监测。
2. 前约 30 秒出现间歇噪声，随后约 30 秒保持稳定安静。
3. 在噪声详情“按日期汇总”中展开当日历史，查看第二个片段。

当片段落盘与实时分析在同一帧触发时，第二个片段的评分会包含前一片段的噪声活动。记录中的起止时间、帧数和平均声级来自当前 30 秒，评分、事件数等指标却可能来自最近 60 秒。

### 原因与源码依据

1. [采样参数](../src/utils/noiseService.js#L14)定义 100ms 帧周期、500ms 实时分析间隔、60 秒评分窗口和 30 秒历史片段。
2. [实时分析](../src/utils/noiseService.js#L242)使用 `windowFrames` 计算滚动窗口结果。
3. **[片段结束分支](../src/utils/noiseService.js#L255)** 优先把本帧的实时 `analysis` 传给 `finalizeSlice`；只有本帧没有实时分析时，才单独分析 `sliceFrames`。
4. [生成历史记录](../src/utils/noiseService.js#L326)保存当前片段的 `start/end/frames` 和响度均值，却同时采用传入分析结果的评分、事件数、覆盖率等指标。
5. [历史界面说明](../src/components/NoiseMonitorDetail.vue#L563)明确写着“每个片段约 30 秒”，并按[该片段的起止时间和评分](../src/components/NoiseMonitorDetail.vue#L625)展示记录。[日汇总](../src/utils/noiseHistorySummary.js#L23)又对这些历史评分求平均，因此影响会进入日均分。

这里的问题是历史区间统计与其时间范围不一致；实时界面使用滚动窗口本身无需改变。

### 轻量复现

调用实际 `consumeFeature()`，以模拟时钟每 100ms 输入一帧：前 30 秒在 −25/−60 dBFS 之间交替，后 30 秒固定为 −60 dBFS。使用同一个实际分析函数，只分析第二片段自身帧，作为对照。

| 指标 | 实际保存的第二片段 | 仅分析第二片段自身帧 |
| --- | --- | --- |
| 片段长度 | 30 秒 / 300 帧 | 30 秒 / 300 帧 |
| 安静评分 | 49 | 100 |
| 噪声事件数 | 16 | 0 |

此外，首个完整 30 秒片段被保存为覆盖率 `50%`、质量 `low-coverage`，也是借用了 60 秒分析窗口的结果。

真实设备采样调度可能使部分片段走到正确分支，因此不是每个片段都必然错误。上述标准 100ms 帧节奏能够稳定触发；未使用真实麦克风验证。

### 建议与修复验收

- 历史片段始终使用该片段的 `sliceFrames` 单独计算，明确窗口时长；实时滚动评分继续独立计算。
- 覆盖正常完成的 30 秒片段和停止监测时的不足 30 秒尾片段，保证评分、覆盖率、事件数与记录时间范围一致。
- 验收包含“先吵后静”和“先静后吵”，并让片段完成分别与实时分析同帧、错帧发生，保证历史结果不依赖调度巧合。

## 从这四项问题得到的工程改进方向

这些问题不需要先做大范围重构即可修复，但各自暴露了可复用的边界约束：

| 边界 | 当前缺口 | 建议形成的约束 |
| --- | --- | --- |
| 分页 API → 页面列表 | 当前页被当成完整结果集 | 显式区分当前页数量与全量数量；筛选、计数、加载范围一致 |
| 名单 → 考勤 | 名单已持久化，关联考勤只在局部内存清理 | 明确当前记录与历史快照的关联策略；读取、编辑、保存使用一致规则 |
| 表单 → store | 组件本地失败依赖 store 提供错误 | 提交前验证输入；每个会抛错的层级都能把失败解释给用户 |
| 实时窗口 → 历史记录 | 不同时间范围共用一次分析结果 | 每项统计附着于明确的时间范围，避免通过可选参数混用不同窗口 |

建议先补齐上述四条具体操作的回归用例，再按这些约束检查相邻功能。回归应验证用户可见结果，而不只是 API 请求成功或函数没有抛错。
